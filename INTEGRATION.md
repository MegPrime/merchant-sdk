# MegPrime checkout: server-side integration (secret key)

**This is a build spec for a coding agent** (Lovable, Cursor, Claude Code, and
so on). Paste the whole file into the agent. It covers taking payments into a
MegPrime store from an app whose **server works out the price**: bookings,
baskets, shipping, tax, anything calculated.

If every price is fixed and registered in advance, use the publishable-key
path in the package README instead. That path needs no server.

---

## 0. Rules the agent must not break

1. **The secret key (`msk_…`) never reaches the browser.** It must never go in
   frontend code, a `VITE_*` or `NEXT_PUBLIC_*` variable, a URL, logs, or the
   database. It is read from a server-side secret and used only in server code.
2. **The browser never sends an amount.** It sends an order id. The server
   loads the order from its own database and computes the total there. A total
   computed in the browser is a total the buyer chooses.
3. **The browser never decides that an order is paid.** `onSuccess` in the page
   is for updating the UI. Before releasing goods, the server re-checks the
   payment status itself (section 5).
4. **Amounts are strings in minor units, never floats.** `$12.50` is
   `"12500000"` (6 decimals). Use integer or BigInt arithmetic.
5. **Use one `client_ref` per payment attempt, not per click.** It must be a
   UUID, stored on the order before the call. A retry that sends the same
   `client_ref` gets the same payment request back, so the buyer isn't charged
   twice. Only issue a new one when the old request can no longer be used: it
   expired, it was cancelled, or the order total changed.
6. **Branch on error codes, never on message text.**

---

## 1. What the merchant gives you

These are provided by the store owner, not generated by the agent. The owner
mints a **secret** key (not a publishable `mpk_` key) for their store and hands
it over:

| Name | Example | Where it goes |
|---|---|---|
| `MEGPRIME_SECRET_KEY` | `msk_…` | server secret only |
| `MEGPRIME_GATEWAY` | `https://api.megprimepay.com` | server config (optional, this is the default) |

The key is **bound to one store**. It can create payment requests that pay
that store and read that store's requests back, propose refunds of its own
sales, and manage the store's webhooks (section 9). It can't approve a refund,
see another store, or choose a wallet. The merchant may also have set a
maximum amount per request on it.

If the key is missing, stop and ask the human for it. Don't invent a
placeholder that looks like a real key.

## 2. How it works

```
Buyer's browser                 Your server                        MegPrime
───────────────                 ───────────                        ────────
"Pay" for order 123 ─────────►  load order 123 from DB
                                compute total (minor units)
                                POST /api/v1/mpmerchant/server/pay-requests
                                  X-Secret-Key: msk_…
                                  { notional_uoa, client_ref } ──►  creates request
                                save fulfillment_id on order  ◄──  { fulfillment_id, … }
attachCheckout(fulfillmentId) ◄─ return { fulfillmentId }
shows QR + "Open in app"
polls status (no credential) ─────────────────────────────────►  GET /fulfillments/{id}/status
onSuccess ──────────────────►   GET status again, check paid_sum ►
                                mark order paid, release goods
```

## 4. Server: create the payment request

### The API

```
POST {MEGPRIME_GATEWAY}/api/v1/mpmerchant/server/pay-requests
Content-Type: application/json
X-Secret-Key: msk_…

{
  "notional_uoa": "12500000",     // required. positive integer string, minor units, ≤ 39 digits
  "client_ref":   "<attempt uuid>", // strongly recommended. must be a UUID
  "memo":         "Booking #123"  // optional. ≤ 200 chars, shown to the merchant
}
```

Success is `201` (new) or `200` (the existing request for this `client_ref`):

```json
{
  "success": true,
  "data": {
    "id": "…",
    "fulfillment_id": "…",
    "notional_uoa": "12500000",
    "currency": { "symbol": "USDC", "decimals": 6, "address": "0x…", "chain_id": 8453 },
    "deadline": "2026-09-15T18:00:00Z",
    "status": "pending",
    "client_ref": "…"
  }
}
```

Errors look like `{ "error": "<code>" }`:

| HTTP | `error` | What to do |
|---|---|---|
| 401 | `publishable_key_invalid` | The key is wrong, revoked, or expired, or it's a `mpk_` key. Don't retry. Tell the operator. |
| 422 | `invalid_amount` | Your amount isn't a positive integer string. This is a bug in your code. |
| 422 | `amount_over_key_cap` | The total is above the cap the merchant set on this key. Don't retry. |
| 400 | `invalid_body` | Malformed JSON, `client_ref` isn't a UUID, or `memo` is over 200 characters. |
| 429 | `rate_limited` | Back off, then retry with the **same** `client_ref`. |
| 503 | `embedded_payments_unavailable`, `payment_requests_unavailable`, `store_payee_unavailable` | Problem on the merchant's side. Retry later with the **same** `client_ref`. |

### Special case: `unconfirmed`

A successful response can still come back with **no `fulfillment_id`** and
`status: "unconfirmed"`. That means MegPrime didn't hear back from its payment
core, so it's **unknown** whether a payable request exists. **Don't show a QR.**
Tell the buyer the payment couldn't be started. Retrying with the same
`client_ref` is safe and returns the same record once it resolves.

### Currency scale

The settlement token is currently USDC with 6 decimals, so dollars × 1,000,000
gives minor units. **Don't trust that silently.** After creating the request,
check that `data.currency.decimals` matches the scale you used. If it doesn't,
refuse to show the checkout and log loudly. A price shown at the wrong scale
is a wrong price.

### Payer token vs settlement token

The payer pays in **MPP** (18 decimals) through the Z5 router; the store
settles in **USDC** through its router plan. Request amounts (`notional_uoa`,
`amountUoa`) stay **USDC, 6 dp**. The public pay-details response adds
`input_token` (the MPP address) and `input_decimals` (18), typed as
`PublicPayDetails`. Never scale a request amount by `input_decimals`.

### Reference implementation: Supabase Edge Function (Lovable)

Store the key with `supabase secrets set MEGPRIME_SECRET_KEY=msk_…`, or use
Lovable's **Secrets** panel. Don't put it in `.env` files that ship to the
client.

`supabase/functions/megprime-create-payment/index.ts`:

```ts
import { createClient } from 'npm:@supabase/supabase-js@2';

const GATEWAY = Deno.env.get('MEGPRIME_GATEWAY') ?? 'https://api.megprimepay.com';
const SECRET_KEY = Deno.env.get('MEGPRIME_SECRET_KEY')!;
const DECIMALS = 6; // USDC. Checked against the response below.

const cors = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Headers': 'authorization, x-client-info, apikey, content-type',
};

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') return new Response('ok', { headers: cors });
  const json = (body: unknown, status = 200) =>
    new Response(JSON.stringify(body), { status, headers: { ...cors, 'Content-Type': 'application/json' } });

  // The caller's own session, so they can only pay for THEIR order.
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_ANON_KEY')!,
    { global: { headers: { Authorization: req.headers.get('Authorization') ?? '' } } },
  );

  const { orderId } = await req.json().catch(() => ({}));
  if (!orderId) return json({ error: 'order_required' }, 400);

  // The ONLY source of the amount. Never read a price from the request body.
  const { data: order, error } = await supabase
    .from('orders')
    .select('id, status, total_cents, payment_attempt_id, payment_amount_uoa, payment_status, fulfillment_id')
    .eq('id', orderId)
    .single();
  if (error || !order) return json({ error: 'order_not_found' }, 404);
  if (order.status === 'paid') return json({ error: 'already_paid' }, 409);

  // cents → minor units, integer math only. 1 cent = 10^(DECIMALS-2) minor units.
  const notional = (BigInt(order.total_cents) * 10n ** BigInt(DECIMALS - 2)).toString();

  // Service role for writes, because this is the server recording a fact.
  const admin = createClient(Deno.env.get('SUPABASE_URL')!, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!);

  // Reuse the current attempt unless it can no longer be paid. Reusing is what
  // makes a double tap or a lost response return the SAME request. A new
  // attempt is needed only when the old request is dead or is for a different
  // amount, because MegPrime returns the original request for a reused ref.
  const DEAD = ['expired', 'cancelled', 'declined', 'failed', 'voided'];
  let deadUpstream = false;
  if (order.fulfillment_id) {
    // Our row may not have caught up (e.g. the confirm job hasn't run since it
    // expired), so ask MegPrime. A failed lookup is UNKNOWN: reuse the attempt,
    // which at worst returns the old request again. It never double charges.
    const st = await fetch(`${GATEWAY}/api/v1/enforcer/fulfillments/${encodeURIComponent(order.fulfillment_id)}/status`)
      .then((r) => (r.ok ? r.json() : null)).catch(() => null);
    deadUpstream = DEAD.includes(String(st?.data?.status ?? '').toLowerCase());
  }
  const needNewAttempt =
    !order.payment_attempt_id ||
    order.payment_amount_uoa !== notional ||
    DEAD.includes(order.payment_status) ||
    deadUpstream;
  let attemptId: string = order.payment_attempt_id;
  if (needNewAttempt) {
    attemptId = crypto.randomUUID();
    // Saved BEFORE the call, so a retry after a lost response reuses it. If
    // this write fails, stop: calling anyway would let the next retry mint yet
    // another attempt, and that is how one order gets two payment requests.
    const { error: saveErr } = await admin.from('orders').update({
      payment_attempt_id: attemptId,
      payment_amount_uoa: notional,
      payment_status: 'creating',
      fulfillment_id: null,
    }).eq('id', order.id);
    if (saveErr) return json({ error: 'order_update_failed' }, 500);
  }

  const res = await fetch(`${GATEWAY}/api/v1/mpmerchant/server/pay-requests`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-Secret-Key': SECRET_KEY },
    body: JSON.stringify({
      notional_uoa: notional,
      client_ref: attemptId,           // one per ATTEMPT. A retry returns the same request.
      memo: `Order ${order.id}`,
    }),
  });
  const body = await res.json().catch(() => ({}));
  if (!res.ok) {
    console.error('megprime create failed', res.status, body.error); // never log the key
    return json({ error: body.error ?? 'payment_create_failed' }, res.status >= 500 ? 502 : 400);
  }

  const data = body.data ?? {};
  if (!data.fulfillment_id) {
    // unconfirmed: whether a payable request exists is UNKNOWN. No QR.
    return json({ error: 'payment_unconfirmed' }, 503);
  }
  if (data.notional_uoa !== notional) {
    // Should be impossible after the attempt logic above. If it happens, the
    // request MegPrime returned is for a different amount. Never show it.
    console.error('megprime amount mismatch', data.notional_uoa, notional);
    return json({ error: 'amount_mismatch' }, 409);
  }
  if (data.currency && data.currency.decimals !== DECIMALS) {
    console.error('megprime currency scale mismatch', data.currency);
    return json({ error: 'currency_mismatch' }, 500);
  }

  await admin.from('orders').update({
    fulfillment_id: data.fulfillment_id,
    payment_status: 'awaiting_payment',
  }).eq('id', order.id);

  // The browser gets the id and nothing else.
  return json({ fulfillmentId: data.fulfillment_id, deadline: data.deadline });
});
```

This needs four columns on the order: `payment_attempt_id uuid`,
`payment_amount_uoa text`, `payment_status text` and `fulfillment_id text`
(plus `paid_at timestamptz` for section 5). Adjust the table and column names to
match the app. **Keep the shape:** load the order, compute on the server, reuse
the attempt's `client_ref` unless the old request is dead or for a different
amount, and return only the `fulfillmentId`.

For another backend (Node, Next.js route handler, Python, Go), make the same
single HTTP call. The rules in section 0 still apply.

### Using the SDK instead of raw HTTP (optional)

The same call, with the amount and key checks done for you. It **refuses to run
in a browser**, so importing it into a component fails loudly instead of leaking
the key:

```ts
import { createPaymentRequest } from '@megprime/merchant-sdk/server';

const sale = await createPaymentRequest({
  secretKey: Deno.env.get('MEGPRIME_SECRET_KEY')!,
  amountUoa: notional,      // minor units, integer string
  clientRef: attemptId,
  memo: `Order ${order.id}`,
});
// sale.fulfillmentId, sale.payUrl, sale.walletPayUrl, sale.currency, sale.deadline
```

Two payer links come back. `payUrl` (https://app.megprimepay.com/send?fulfillment_id=<id>)
is for MegPrime users. `walletPayUrl` (https://merchant.megprimepay.com/send?fulfillment_id=<id>)
is for anyone with a Base wallet holding USDC; it needs no MegPrime account.
The wallet link is for the test store only until MegPrime decides on KYC.
Show whichever fits the payer, or both as two QR codes
(`appQrSvg(id)` / `walletQrSvg(id)`).

## 5. Server: confirm payment before releasing goods

Whatever tells you a payment may have landed (the page's `onSuccess`, a
`payment_request.paid` webhook (section 9), or a scheduled job), the server
makes the final check itself. The status endpoint is public and needs no
credential:

```
GET {MEGPRIME_GATEWAY}/api/v1/enforcer/fulfillments/{fulfillment_id}/status
```

```json
{ "success": true,
  "data": { "id": "…", "status": "confirmed", "settled_at": "…",
            "notional_uoa": "12500000", "paid_sum": "12500000" } }
```

An order is paid **only if both** of these hold:

- `status` is `confirmed` or `settled`
- `BigInt(paid_sum) >= BigInt(notional_uoa)`, and `notional_uoa` equals the
  amount your server sent for this order

Treat a status of `expired`, `cancelled`, `declined`, `failed`, or `voided` as
not paid. Any other status means the payment is still in progress. A failed or
non-200 status call means **unknown**, not unpaid.

`supabase/functions/megprime-confirm-payment/index.ts`:

```ts
import { createClient } from 'npm:@supabase/supabase-js@2';

const GATEWAY = Deno.env.get('MEGPRIME_GATEWAY') ?? 'https://api.megprimepay.com';
const DECIMALS = 6;
const PAID = new Set(['confirmed', 'settled']);
const DEAD = new Set(['expired', 'cancelled', 'declined', 'failed', 'voided']);

const cors = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Headers': 'authorization, x-client-info, apikey, content-type',
};

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') return new Response('ok', { headers: cors });
  const json = (body: unknown, status = 200) =>
    new Response(JSON.stringify(body), { status, headers: { ...cors, 'Content-Type': 'application/json' } });

  const { orderId } = await req.json().catch(() => ({}));
  const admin = createClient(Deno.env.get('SUPABASE_URL')!, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!);

  // The fulfillment id comes from OUR row, never from the request.
  const { data: order } = await admin
    .from('orders').select('id, status, total_cents, fulfillment_id, payment_amount_uoa').eq('id', orderId).single();
  if (!order?.fulfillment_id) return json({ state: 'unknown' }, 404);
  if (order.status === 'paid') return json({ state: 'paid' });

  const res = await fetch(`${GATEWAY}/api/v1/enforcer/fulfillments/${encodeURIComponent(order.fulfillment_id)}/status`);
  if (!res.ok) return json({ state: 'unknown' }, 502);
  const { data } = await res.json();

  // What was sent for this attempt, and it must still be the order's total.
  const expected = order.payment_amount_uoa;
  const currentTotal = (BigInt(order.total_cents) * 10n ** BigInt(DECIMALS - 2)).toString();
  if (!expected || expected !== currentTotal) return json({ state: 'unknown' }, 409);
  const status = String(data?.status ?? '').toLowerCase();

  if (PAID.has(status)) {
    const paidEnough =
      /^\d+$/.test(data.paid_sum ?? '') &&
      data.notional_uoa === expected &&
      BigInt(data.paid_sum) >= BigInt(expected);
    if (!paidEnough) return json({ state: 'settling' }); // underpaid or still arriving
    // Idempotent: only the first confirm flips it.
    await admin.from('orders')
      .update({ status: 'paid', payment_status: 'paid', paid_at: data.settled_at ?? new Date().toISOString() })
      .eq('id', order.id).neq('status', 'paid');
    return json({ state: 'paid' });
  }
  if (DEAD.has(status)) {
    await admin.from('orders').update({ payment_status: status }).eq('id', order.id);
    return json({ state: status === 'expired' ? 'expired' : 'cancelled' });
  }
  return json({ state: 'settling' });
});
```

Call this endpoint from the page's `onSuccess`. To catch buyers who close the
tab after paying, also call it from a scheduled job (for example a Supabase cron
running every minute) for orders in `awaiting_payment` whose deadline hasn't
passed by more than a few minutes.

## 6. Browser: render and watch

```tsx
import { useEffect, useRef, useState } from 'react';
import { attachCheckout, type CheckoutHandle } from '@megprime/merchant-sdk';
import { supabase } from '@/integrations/supabase/client';

export function PayWithMegPrime({ orderId, onPaid }: { orderId: string; onPaid: () => void }) {
  const ref = useRef<HTMLDivElement>(null);
  const [error, setError] = useState<string>();
  const [canRestart, setCanRestart] = useState(false);
  // Bumping this re-runs the effect. The server decides whether that reuses
  // the current request or issues a new one (section 4).
  const [attempt, setAttempt] = useState(0);

  useEffect(() => {
    let checkout: CheckoutHandle | undefined;
    let cancelled = false;
    setError(undefined);
    setCanRestart(false);

    (async () => {
      // Send the ORDER ID. Never an amount.
      const { data, error } = await supabase.functions.invoke('megprime-create-payment', {
        body: { orderId },
      });
      if (cancelled) return;
      if (error || !data?.fulfillmentId) {
        setError("We couldn't start this payment. Please try again.");
        setCanRestart(true);
        return;
      }

      checkout = attachCheckout({
        fulfillmentId: data.fulfillmentId,
        container: ref.current!,
        theme: 'auto',
        onSuccess: async () => {
          // The UI says paid. The SERVER decides whether it is.
          const { data: c } = await supabase.functions.invoke('megprime-confirm-payment', {
            body: { orderId },
          });
          if (c?.state === 'paid') onPaid();
        },
        onError: (err) => setError(err.retryable ? 'Connection problem, retrying…' : err.message),
        onCancel: () => { /* widget closed. The request may STILL be paid. */ },
        onStateChange: (state) => {
          if (state === 'expired') {
            setError('This payment window expired. Start again to get a new code.');
            setCanRestart(true);
          }
        },
      });
      await checkout.start();
    })();

    return () => { cancelled = true; checkout?.destroy(); };
  }, [orderId, attempt]);

  return (
    <div>
      {error && <p role="alert">{error}</p>}
      {canRestart && <button type="button" onClick={() => setAttempt((n) => n + 1)}>Start again</button>}
      {/* keyed so a restart gets a fresh element: the widget attaches a shadow root, which can't be attached twice */}
      <div key={`${orderId}-${attempt}`} ref={ref} />
    </div>
  );
}
```

The widget renders a QR code, an "Open in the app" deeplink, and live status
inside a shadow root. The app's CSS won't leak into it. **Show the order total
yourself** above the widget, from your own order data. In this mode the widget
doesn't know the currency scale, so it deliberately shows no amount.

For a custom UI instead of the bundled widget, omit `container`. Then draw a QR
from `checkout.snapshot.payUrl` (app) or `checkout.snapshot.walletPayUrl` (any Base wallet with USDC, no account, test store only for now) and react to `onStateChange(state, snapshot)`.

### States

| state | meaning |
|---|---|
| `awaiting_payment` | QR is live |
| `settling` | a payer committed and the payment is confirming |
| `paid` | **terminal.** Now confirm on the server (section 5) |
| `expired` | **terminal.** The window closed unpaid. This isn't an error. Offer to start again |
| `cancelled` | **terminal.** The widget was closed. The request may **still be paid** |
| `error` | **terminal.** See `snapshot.error.code` |

`snapshot.consecutiveFailures > 0` means the answer is currently **unknown**. Show
"Reconnecting…", never "Unpaid".

## 7. Edge cases the agent must handle

- **Buyer taps Pay twice, or the network drops mid-create.** The stored
  `payment_attempt_id` is reused, so the server call returns the same request.
  Don't generate a new `client_ref` per click.
- **Buyer wants a new code after `expired`.** The create function sees the dead
  status and issues a new `payment_attempt_id` automatically. "Start again" just
  calls it again. Reusing the old `client_ref` would return the expired request.
- **Widget closed, or the page navigated away.** Closing doesn't cancel anything.
  A buyer with a screenshot of the QR can still pay until the deadline. Keep the
  order `awaiting_payment` and let the server confirmation job settle it.
- **Order total changes after a request exists** (item added, coupon applied).
  The existing request is frozen at the old amount, and resending the same
  `client_ref` would return it unchanged. The create function sees that the
  total no longer matches `payment_amount_uoa` and issues a new attempt. Section
  5 refuses to mark the order paid if the stored amount doesn't match the
  current total.
- **Underpayment.** Handled by the `paid_sum >= notional_uoa` check. Never mark
  paid on status alone.

## 8. Refunds

For a sale your secret key created, a refund is an entry in MegPrime's ledger,
settled with **you, off-chain, by wire**. You then settle with your customer.
Nothing moves on-chain and there is no refund payment to watch.

- **At or under your key's auto-refund limit** (100 USDC per refund and 500 USDC
  per UTC day by default; MegPrime sets them, your key cannot), the refund comes
  back **`owed` immediately**: no person involved.
- **Above it**, it stays **`proposed`** until the store owner approves (→ `owed`)
  or rejects it.
- **`wired`** means MegPrime has sent the wire.
- **Nobody names a destination**, and a refund can **never exceed what the sale
  actually received**, minus refunds already recorded (`422 refund_exceeds_paid`).
- **Retries are safe:** the same `clientRef` returns the same refund, never a
  second one.

```ts
import { proposeRefund, getRefundProposal }
  from '@megprime/merchant-sdk/server';

// 1. ask (server-side, from your own cancellation flow)
const refund = await proposeRefund({
  secretKey: Deno.env.get('MEGPRIME_SECRET_KEY')!,
  fulfillmentId: order.fulfillment_id,
  amountUoa: order.payment_amount_uoa,   // partial refunds are fine
  reason: 'Booking cancelled by the guest',
  clientRef: refundDecisionId,           // a retry returns the SAME refund
});
// store refund.id on the order

// 2. act on the state; poll getRefundProposal only while it is 'proposed'
const now = refund.state === 'proposed'
  ? await getRefundProposal({ secretKey, proposalId: refund.id })
  : refund;
switch (now.state) {
  case 'owed':     /* MegPrime owes you this amount; refund your customer */ break;
  case 'wired':    /* the wire has been sent */ break;
  case 'proposed': /* over the limit: waiting on the merchant */ break;
  case 'rejected':
  case 'failed':   /* now.decisionReason says why */ break;
}
```

**Show the customer a QR only for a sale**, never for a refund: refunds are
settled with you by wire, not paid on-chain.

## 9. Webhooks

Webhooks tell your server the moment a payment or refund changes. Every route
below is under `https://api.megprimepay.com/api/v1/mpmerchant`, authenticated by
the store's secret key in `X-Secret-Key`, and scoped to that key's store
(another store's endpoint or event is a 404, never a 403). All of it is
server-side only.

### Register an endpoint and store the secret

```ts
import { createWebhookEndpoint } from '@megprime/merchant-sdk/server';

const ep = await createWebhookEndpoint({
  secretKey: process.env.MEGPRIME_SECRET_KEY!,
  url: 'https://shop.example/hooks/megprime',
  description: 'production',            // optional, 500 characters or fewer
});
// ep.secret is the signing secret (whsec_…). It is returned ONCE, here, and
// never again: write it straight into your server-side secret store as
// MEGPRIME_WHSEC. Do not log it. Lost it? rotateWebhookSecret.
```

Raw HTTP: `POST /server/webhook-endpoints` with `{ "url": "…", "description": "…" }`
returns `201` and `data.secret`.

- The URL must be **https on port 443** and resolve to a **public** address
  (`invalid_webhook_url` otherwise), 2048 characters or fewer.
- At most **5 live endpoints** per store (`webhook_endpoint_limit`).
- Every endpoint receives **every** event type. There is no per-endpoint filter:
  ignore the types you don't need, and still answer them `2xx`.
- `listWebhookEndpoints` (`GET /server/webhook-endpoints`) shows `enabled`,
  `disabledReason` and `consecutiveFailures`. It never returns a secret.
- `deleteWebhookEndpoint` (`DELETE /server/webhook-endpoints/{id}`) stops
  delivery; deliveries still pending for it fail without retry.

### Verify every delivery

Each delivery is a `POST` with `Content-Type: application/json` and these
headers:

| header | value |
|---|---|
| `X-MegPrime-Signature` | `t=<unix>,v1=<hex>`, and one more `v1=` per extra live secret during a rotation |
| `X-MegPrime-Event-Id` | `evt_…`, same as the body's `id` |
| `X-MegPrime-Event-Type` | the event type |
| `X-MegPrime-Delivery-Id` | per endpoint; not a dedupe key |
| `User-Agent` | `MegPrime-Webhooks/1` |

`v1` is `hex(HMAC-SHA256(secret, "<t>.<raw body>"))`. The key is the **whole**
`whsec_…` string as UTF-8, prefix included; don't decode it.

`verifyWebhook(rawBody, signatureHeader, secrets, { toleranceSeconds })` from
`@megprime/merchant-sdk/server` checks it and returns the parsed event:

- **Pass the raw body**: the exact bytes received, as a `Buffer`, `Uint8Array`,
  `ArrayBuffer` or string. If a JSON body parser runs first, re-serialising
  changes whitespace and key order and the signature won't match. Passing a
  parsed object throws a `TypeError`, a bug in your route rather than a bad
  delivery.
- `secrets` is one secret or an array. **Any `v1` matching any secret passes**,
  which is how a rotation overlap works.
- A timestamp more than `toleranceSeconds` (default **300**) from your clock,
  **in the past or the future**, is refused. Keep your server clock on NTP.
- MACs are compared in constant time.
- A failure throws `WebhookSignatureError` with `code`:
  `malformed` (missing header, a segment without `=`, no or repeated `t`, a `v1`
  that isn't 64 hex, a body that isn't JSON), `stale` (outside the tolerance) or
  `no_match`. **Answer `400` and do nothing.** Unknown schemes such as `v0=` are
  ignored.

**Node / Express.** Put `express.raw` on the webhook route, before any global
`express.json()` reaches it:

```ts
import express from 'express';
import { verifyWebhook, WebhookSignatureError, type WebhookEvent } from '@megprime/merchant-sdk/server';

const app = express();
const secrets = [process.env.MEGPRIME_WHSEC!, process.env.MEGPRIME_WHSEC_PREVIOUS].filter(Boolean) as string[];

app.post('/hooks/megprime', express.raw({ type: 'application/json' }), (req, res) => {
  let event: WebhookEvent;
  try {
    event = verifyWebhook(req.body, req.headers['x-megprime-signature'], secrets);  // req.body is a Buffer
  } catch (e) {
    if (e instanceof WebhookSignatureError) return res.sendStatus(400);
    throw e;
  }
  // Insert event.id into a table with a UNIQUE constraint. A duplicate means
  // you already have it: still answer 2xx. Queue the work and return now.
  enqueue(event);
  res.sendStatus(204);
});

app.use(express.json()); // other routes, AFTER the webhook route
```

**Framework-agnostic (fetch `Request`: Next.js route handlers, Hono, Bun, Deno,
Supabase Edge Functions, Cloudflare Workers with `nodejs_compat`):**

```ts
import { verifyWebhook, WebhookSignatureError } from '@megprime/merchant-sdk/server';

export async function handleMegPrimeWebhook(req: Request): Promise<Response> {
  const raw = new Uint8Array(await req.arrayBuffer());   // bytes, not req.json()
  let event;
  try {
    event = verifyWebhook(raw, req.headers.get('x-megprime-signature'), [MEGPRIME_WHSEC]);
  } catch (e) {
    if (e instanceof WebhookSignatureError) return new Response('bad signature', { status: 400 });
    throw e;
  }
  await recordOnce(event.id, event);                     // dedupe, then queue
  return new Response(null, { status: 204 });
}
```

**Without the SDK (Web Crypto, any runtime).** `crypto.subtle.verify` compares
in constant time:

```ts
async function verifyMegPrime(raw: Uint8Array, header: string | null, secrets: string[], toleranceSec = 300) {
  const parts = (header ?? '').split(',').map((p) => p.trim().split('='));
  const ts = parts.filter(([k]) => k === 't').map(([, v]) => v);
  const v1 = parts.filter(([k]) => k === 'v1').map(([, v]) => v).filter((h) => /^[0-9a-f]{64}$/i.test(h));
  if (ts.length !== 1 || !/^\d+$/.test(ts[0]) || v1.length === 0) return false;
  if (Math.abs(Date.now() / 1000 - Number(ts[0])) > toleranceSec) return false;
  const signed = new Uint8Array([...new TextEncoder().encode(`${ts[0]}.`), ...raw]);
  for (const s of secrets) {
    const key = await crypto.subtle.importKey('raw', new TextEncoder().encode(s), { name: 'HMAC', hash: 'SHA-256' }, false, ['verify']);
    for (const h of v1) {
      const mac = Uint8Array.from(h.match(/../g)!, (b) => parseInt(b, 16));
      if (await crypto.subtle.verify('HMAC', key, mac, signed)) return true;
    }
  }
  return false;
}
```

Supabase: deploy the receiving function with `--no-verify-jwt`. MegPrime sends
no `Authorization` header; the signature is the authentication.

### Events and payload

Every body has this envelope. It's the same object `listEvents` returns:

```json
{
  "id": "evt_0123456789abcdef0123456789abcdef",
  "type": "payment_request.paid",
  "created_at": "2026-10-12T22:00:00Z",
  "api_version": "2026-10-12",
  "data": { "object": { "…": "the payment request or refund, snake_case" } }
}
```

`id` is stable across retries and redeliveries: **dedupe on it**. Delivery is
at-least-once and **not ordered**, so act on the object's own `status`/`state`
and timestamps, not on arrival order. `data.object` is the resource as it was
when the event was cut, in the wire's snake_case (types: `PaymentRequestEvent`,
`RefundEvent`, `WebhookTestEvent`; `WEBHOOK_EVENT_TYPES` lists them all). Treat
an unknown `type` as "ignore and answer 2xx": new types can be added.

| type | when | `data.object` |
|---|---|---|
| `payment_request.paid` | the payments core reports the sale confirmed or settled | payment request + `tx_hash` |
| `payment_request.failed` | upstream status became `failed`, `expired`, `cancelled` or `declined` (see `status`) | payment request |
| `payment_request.expired` | 60s past `deadline` and still unpaid | payment request |
| `payment_request.voided` | store staff voided it in the MegPrime app (`voided_at`) | payment request |
| `refund.proposed` | a refund over your key's auto-refund limit is waiting on the owner | refund |
| `refund.owed` | approved, automatically (`decided_by: "system:auto"`) or by the owner. MegPrime owes it and settles by wire | refund |
| `refund.rejected` | the owner rejected it (`decision_reason`) | refund |
| `refund.wired` | MegPrime sent the wire (`wired_at`). **This is the money moving** | refund |
| `refund.failed` | an on-chain refund the payments core refused (`decision_reason`); not used for secret-key sales | refund |
| `webhook.test` | you called `sendTestWebhook` | `{ "endpoint_id": "…" }` |

**Payment request object:** `id` (request id), `fulfillment_id`, `store_id`,
`terminal_id`, `client_ref`, `notional_uoa` (minor units, string), `currency`
(`symbol`, `decimals`, `address`, `chain_id`), `memo`, `reference`,
`receiver_wallet`, `request_token`, `chain_id`, `device_paired`, `deadline`,
`status` (the payments core's last status, not normalised: lowercase it),
`status_at`, `settled_at`, `voided_at`, `created_at`, `updated_at`; plus
`tx_hash` on `payment_request.paid`. Match it to your order by `client_ref` or
`fulfillment_id`.

**`payment_request.paid` is not proof of the amount.** It fires on the upstream
status, and the object has no `paid_sum`. Before releasing goods, call
`getPaymentStatus(fulfillment_id)` and require `paidUoa >= amountUoa`, as in
section 5. A webhook replaces your polling *trigger*, not
that check. Payment events come from a sweeper that runs about every 10s, so
expect a few seconds of lag after the chain.

**Refund object:** `id`, `request_id` (the sale's request id), `store_id`,
`amount_uoa`, `reason`, `state`, `settlement` (`off_chain` for secret-key
sales), `client_ref`, `decided_by`, `decided_at`, `decision_reason`,
`wired_at`, `refund_fulfillment_id`, `refund_destination`,
`proposed_by_key_id`, `created_at`, `updated_at`. Finance's wire reference is
never included.

### Retries and auto-disable

- A delivery succeeds on any **2xx** within **10 seconds**. Redirects are not
  followed. Anything else, including a timeout or a 3xx, is a failed attempt.
  Answer fast and do the work afterwards.
- A failed delivery is retried with backoff, **12 attempts in all**. The waits
  after each failure are 30s, 2m, 10m, 30m, 1h, 2h, 4h, 8h, 12h, 12h, 12h, so
  the last attempt is about **52 hours** after the first. After the 12th the
  delivery is `failed`.
- Each delivery that ends `failed` adds one to the endpoint's
  `consecutiveFailures`; any success resets it to 0. At **10 consecutive failed
  deliveries** the endpoint is **disabled**, with
  `disabledReason: "auto-disabled after 10 consecutive failed deliveries"`.
- While an endpoint is disabled, new events are **not queued** for it and its
  pending deliveries fail at once. They aren't lost: they're in `listEvents`.

### Re-enable

Fix the receiver first, or it will disable again. Then:

```ts
await enableWebhookEndpoint({ secretKey, endpointId });  // POST /server/webhook-endpoints/{id}/enable
await sendTestWebhook({ secretKey, endpointId });         // check it end to end
// then gap-fill (below) from the last event you processed
```

`enable` clears `disabledReason` and resets `consecutiveFailures` to 0.

### Rotate the secret (24h overlap)

```ts
const { secret } = await rotateWebhookSecret({ secretKey, endpointId });
// POST /server/webhook-endpoints/{id}/rotate-secret: the new whsec_, ONCE
```

The **previous secret keeps working for 24 hours**. During that window every
delivery is signed with **both**, so the header carries two `v1=` values. A
receiver still on the old secret keeps verifying, and so does one already on
the new secret. To roll over:

1. Rotate and store the new secret as `MEGPRIME_WHSEC`, keeping the old one as
   `MEGPRIME_WHSEC_PREVIOUS`.
2. Deploy with `verifyWebhook(raw, sig, [MEGPRIME_WHSEC, MEGPRIME_WHSEC_PREVIOUS])`.
3. Remove the old secret any time after; it stops working 24h after the rotation.

Only the most recent previous secret is kept, so rotating again inside the 24h
ends the earlier overlap at once. That is also how to cut off a **leaked**
secret immediately: rotate **twice**. The leaked secret is dropped, and the
overlap runs on the intermediate one, which never left your hands.

### Gap filling: `GET /server/events?after=`

After downtime, or as a periodic safety net, page through what you may have
missed. Events come **oldest first**, strictly after the event id you pass;
`limit` is 1 to 100 (default 50). An `after` that isn't one of your store's
event ids is `webhook_event_not_found`.

```ts
import { listEvents } from '@megprime/merchant-sdk/server';

let after = await loadCursor();            // an evt_… you have processed, or undefined for the start
for (;;) {
  const page = await listEvents({ secretKey, after, limit: 100 });
  for (const event of page.events) await handleOnce(event);   // same dedupe as the webhook route
  after = page.nextAfter;
  await saveCursor(after);
  if (!page.mayHaveMore) break;
}
```

The feed holds the exact payloads that were (or will be) delivered, including
`webhook.test` events. Events are ordered by the time they were *cut*, which is
inside the transaction that caused them, so one can land just behind a cursor
you have already passed. Re-read from an event a few minutes old rather than
from the very latest, and let dedupe absorb the overlap.

### Redeliver one event

```ts
const { queued } = await redeliverEvent({ secretKey, eventId: 'evt_…' });
// POST /server/events/{id}/redeliver: 202, data.queued = endpoints it was queued for
```

This resets (or creates) a pending delivery of that event for **every enabled
endpoint** of the store, sent on the worker's next tick with a fresh signature
and the full retry schedule. `queued: 0` means no endpoint is enabled.

### Test events

`sendTestWebhook({ secretKey, endpointId })` (`POST
/server/webhook-endpoints/{id}/test`, `202`) queues a `webhook.test` event to
that one endpoint only. It's signed and retried like any other. The response
carries no event id; the delivery and `listEvents` do. Use it after creating,
rotating or re-enabling an endpoint.

### Errors from these routes

| code | status | meaning |
|---|---|---|
| `invalid_webhook_url` | 400 | not https:443, not public, or too long |
| `webhook_endpoint_limit` | 422 | 5 live endpoints already |
| `webhook_endpoint_not_found` | 404 | no live endpoint with that id on this store |
| `webhook_event_not_found` | 404 | no event with that id (or `after`) on this store |
| `payment_request_not_found` | 404 | `getPaymentRequest`: not this store's request |
| `invalid_body` | 400 | bad body or query (e.g. `limit` outside 1..100) |
| `webhooks_unavailable` | 503 | webhooks are switched off server-side; retryable |
| `publishable_key_invalid` | 401 | the secret key is unknown, revoked or malformed |
