# MegPrime checkout: server-side integration (secret key)

**This is a build spec for a coding agent** (Lovable, Cursor, Claude Code, and
so on). Paste the whole file into the agent. It covers taking payments into a
MegPrime store from an app whose **server works out the price**: bookings,
baskets, shipping, tax, anything calculated.

If every price is fixed and registered in advance, use the publishable-key
path in the package README instead. That path needs no server.

---

## 0. Rules the agent must not break

1. **The secret key (`msk_…`) never reaches the browser.** It must never go in
   frontend code, a `VITE_*` or `NEXT_PUBLIC_*` variable, a URL, logs, or the
   database. It is read from a server-side secret and used only in server code.
2. **The browser never sends an amount.** It sends an order id. The server
   loads the order from its own database and computes the total there. A total
   computed in the browser is a total the buyer chooses.
3. **The browser never decides that an order is paid.** `onSuccess` in the page
   is for updating the UI. Before releasing goods, the server re-checks the
   payment status itself (section 5).
4. **Amounts are strings in minor units, never floats.** `$12.50` is
   `"12500000"` (6 decimals). Use integer or BigInt arithmetic.
5. **Use one `client_ref` per payment attempt, not per click.** It must be a
   UUID, stored on the order before the call. A retry that sends the same
   `client_ref` gets the same payment request back, so the buyer isn't charged
   twice. Only issue a new one when the old request can no longer be used: it
   expired, it was cancelled, or the order total changed.
6. **Branch on error codes, never on message text.**

---

## 1. What the merchant gives you

These are provided by the store owner, not generated by the agent. The owner
mints a **secret** key (not a publishable `mpk_` key) for their store and hands
it over:

| Name | Example | Where it goes |
|---|---|---|
| `MEGPRIME_SECRET_KEY` | `msk_…` | server secret only |
| `MEGPRIME_GATEWAY` | `https://api.megprimepay.com` | server config (optional, this is the default) |

The key is **bound to one store** and can do exactly one thing: create payment
requests that pay that store. It can't read payments, list anything, or
choose a wallet. The merchant may also have set a maximum amount per request
on it.

If the key is missing, stop and ask the human for it. Don't invent a
placeholder that looks like a real key.

## 2. How it works

```
Buyer's browser                 Your server                        MegPrime
───────────────                 ───────────                        ────────
"Pay" for order 123 ─────────►  load order 123 from DB
                                compute total (minor units)
                                POST /api/v1/mpmerchant/server/pay-requests
                                  X-Secret-Key: msk_…
                                  { notional_uoa, client_ref } ──►  creates request
                                save fulfillment_id on order  ◄──  { fulfillment_id, … }
attachCheckout(fulfillmentId) ◄─ return { fulfillmentId }
shows QR + "Open in app"
polls status (no credential) ─────────────────────────────────►  GET /fulfillments/{id}/status
onSuccess ──────────────────►   GET status again, check paid_sum ►
                                mark order paid, release goods
```

## 4. Server: create the payment request

### The API

```
POST {MEGPRIME_GATEWAY}/api/v1/mpmerchant/server/pay-requests
Content-Type: application/json
X-Secret-Key: msk_…

{
  "notional_uoa": "12500000",     // required. positive integer string, minor units, ≤ 39 digits
  "client_ref":   "<attempt uuid>", // strongly recommended. must be a UUID
  "memo":         "Booking #123"  // optional. ≤ 200 chars, shown to the merchant
}
```

Success is `201` (new) or `200` (the existing request for this `client_ref`):

```json
{
  "success": true,
  "data": {
    "id": "…",
    "fulfillment_id": "…",
    "notional_uoa": "12500000",
    "currency": { "symbol": "USDC", "decimals": 6, "address": "0x…", "chain_id": 8453 },
    "deadline": "2026-09-15T18:00:00Z",
    "status": "pending",
    "client_ref": "…"
  }
}
```

Errors look like `{ "error": "<code>" }`:

| HTTP | `error` | What to do |
|---|---|---|
| 401 | `publishable_key_invalid` | The key is wrong, revoked, or expired, or it's a `mpk_` key. Don't retry. Tell the operator. |
| 422 | `invalid_amount` | Your amount isn't a positive integer string. This is a bug in your code. |
| 422 | `amount_over_key_cap` | The total is above the cap the merchant set on this key. Don't retry. |
| 400 | `invalid_body` | Malformed JSON, `client_ref` isn't a UUID, or `memo` is over 200 characters. |
| 429 | `rate_limited` | Back off, then retry with the **same** `client_ref`. |
| 503 | `embedded_payments_unavailable`, `payment_requests_unavailable`, `store_payee_unavailable` | Problem on the merchant's side. Retry later with the **same** `client_ref`. |

### Special case: `unconfirmed`

A successful response can still come back with **no `fulfillment_id`** and
`status: "unconfirmed"`. That means MegPrime didn't hear back from its payment
core, so it's **unknown** whether a payable request exists. **Don't show a QR.**
Tell the buyer the payment couldn't be started. Retrying with the same
`client_ref` is safe and returns the same record once it resolves.

### Currency scale

The settlement token is currently USDC with 6 decimals, so dollars × 1,000,000
gives minor units. **Don't trust that silently.** After creating the request,
check that `data.currency.decimals` matches the scale you used. If it doesn't,
refuse to show the checkout and log loudly. A price shown at the wrong scale
is a wrong price.

### Reference implementation: Supabase Edge Function (Lovable)

Store the key with `supabase secrets set MEGPRIME_SECRET_KEY=msk_…`, or use
Lovable's **Secrets** panel. Don't put it in `.env` files that ship to the
client.

`supabase/functions/megprime-create-payment/index.ts`:

```ts
import { createClient } from 'npm:@supabase/supabase-js@2';

const GATEWAY = Deno.env.get('MEGPRIME_GATEWAY') ?? 'https://api.megprimepay.com';
const SECRET_KEY = Deno.env.get('MEGPRIME_SECRET_KEY')!;
const DECIMALS = 6; // USDC. Checked against the response below.

const cors = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Headers': 'authorization, x-client-info, apikey, content-type',
};

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') return new Response('ok', { headers: cors });
  const json = (body: unknown, status = 200) =>
    new Response(JSON.stringify(body), { status, headers: { ...cors, 'Content-Type': 'application/json' } });

  // The caller's own session, so they can only pay for THEIR order.
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_ANON_KEY')!,
    { global: { headers: { Authorization: req.headers.get('Authorization') ?? '' } } },
  );

  const { orderId } = await req.json().catch(() => ({}));
  if (!orderId) return json({ error: 'order_required' }, 400);

  // The ONLY source of the amount. Never read a price from the request body.
  const { data: order, error } = await supabase
    .from('orders')
    .select('id, status, total_cents, payment_attempt_id, payment_amount_uoa, payment_status, fulfillment_id')
    .eq('id', orderId)
    .single();
  if (error || !order) return json({ error: 'order_not_found' }, 404);
  if (order.status === 'paid') return json({ error: 'already_paid' }, 409);

  // cents → minor units, integer math only. 1 cent = 10^(DECIMALS-2) minor units.
  const notional = (BigInt(order.total_cents) * 10n ** BigInt(DECIMALS - 2)).toString();

  // Service role for writes, because this is the server recording a fact.
  const admin = createClient(Deno.env.get('SUPABASE_URL')!, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!);

  // Reuse the current attempt unless it can no longer be paid. Reusing is what
  // makes a double tap or a lost response return the SAME request. A new
  // attempt is needed only when the old request is dead or is for a different
  // amount, because MegPrime returns the original request for a reused ref.
  const DEAD = ['expired', 'cancelled', 'declined', 'failed', 'voided'];
  let deadUpstream = false;
  if (order.fulfillment_id) {
    // Our row may not have caught up (e.g. the confirm job hasn't run since it
    // expired), so ask MegPrime. A failed lookup is UNKNOWN: reuse the attempt,
    // which at worst returns the old request again. It never double charges.
    const st = await fetch(`${GATEWAY}/api/v1/enforcer/fulfillments/${encodeURIComponent(order.fulfillment_id)}/status`)
      .then((r) => (r.ok ? r.json() : null)).catch(() => null);
    deadUpstream = DEAD.includes(String(st?.data?.status ?? '').toLowerCase());
  }
  const needNewAttempt =
    !order.payment_attempt_id ||
    order.payment_amount_uoa !== notional ||
    DEAD.includes(order.payment_status) ||
    deadUpstream;
  let attemptId: string = order.payment_attempt_id;
  if (needNewAttempt) {
    attemptId = crypto.randomUUID();
    // Saved BEFORE the call, so a retry after a lost response reuses it. If
    // this write fails, stop: calling anyway would let the next retry mint yet
    // another attempt, and that is how one order gets two payment requests.
    const { error: saveErr } = await admin.from('orders').update({
      payment_attempt_id: attemptId,
      payment_amount_uoa: notional,
      payment_status: 'creating',
      fulfillment_id: null,
    }).eq('id', order.id);
    if (saveErr) return json({ error: 'order_update_failed' }, 500);
  }

  const res = await fetch(`${GATEWAY}/api/v1/mpmerchant/server/pay-requests`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-Secret-Key': SECRET_KEY },
    body: JSON.stringify({
      notional_uoa: notional,
      client_ref: attemptId,           // one per ATTEMPT. A retry returns the same request.
      memo: `Order ${order.id}`,
    }),
  });
  const body = await res.json().catch(() => ({}));
  if (!res.ok) {
    console.error('megprime create failed', res.status, body.error); // never log the key
    return json({ error: body.error ?? 'payment_create_failed' }, res.status >= 500 ? 502 : 400);
  }

  const data = body.data ?? {};
  if (!data.fulfillment_id) {
    // unconfirmed: whether a payable request exists is UNKNOWN. No QR.
    return json({ error: 'payment_unconfirmed' }, 503);
  }
  if (data.notional_uoa !== notional) {
    // Should be impossible after the attempt logic above. If it happens, the
    // request MegPrime returned is for a different amount. Never show it.
    console.error('megprime amount mismatch', data.notional_uoa, notional);
    return json({ error: 'amount_mismatch' }, 409);
  }
  if (data.currency && data.currency.decimals !== DECIMALS) {
    console.error('megprime currency scale mismatch', data.currency);
    return json({ error: 'currency_mismatch' }, 500);
  }

  await admin.from('orders').update({
    fulfillment_id: data.fulfillment_id,
    payment_status: 'awaiting_payment',
  }).eq('id', order.id);

  // The browser gets the id and nothing else.
  return json({ fulfillmentId: data.fulfillment_id, deadline: data.deadline });
});
```

This needs four columns on the order: `payment_attempt_id uuid`,
`payment_amount_uoa text`, `payment_status text` and `fulfillment_id text`
(plus `paid_at timestamptz` for section 5). Adjust the table and column names to
match the app. **Keep the shape:** load the order, compute on the server, reuse
the attempt's `client_ref` unless the old request is dead or for a different
amount, and return only the `fulfillmentId`.

For another backend (Node, Next.js route handler, Python, Go), make the same
single HTTP call. The rules in section 0 still apply.

## 5. Server: confirm payment before releasing goods

Webhooks don't exist yet. The status endpoint is public and needs no
credential, so the server checks it directly:

```
GET {MEGPRIME_GATEWAY}/api/v1/enforcer/fulfillments/{fulfillment_id}/status
```

```json
{ "success": true,
  "data": { "id": "…", "status": "confirmed", "settled_at": "…",
            "notional_uoa": "12500000", "paid_sum": "12500000" } }
```

An order is paid **only if both** of these hold:

- `status` is `confirmed` or `settled`
- `BigInt(paid_sum) >= BigInt(notional_uoa)`, and `notional_uoa` equals the
  amount your server sent for this order

Treat a status of `expired`, `cancelled`, `declined`, `failed`, or `voided` as
not paid. Any other status means the payment is still in progress. A failed or
non-200 status call means **unknown**, not unpaid.

`supabase/functions/megprime-confirm-payment/index.ts`:

```ts
import { createClient } from 'npm:@supabase/supabase-js@2';

const GATEWAY = Deno.env.get('MEGPRIME_GATEWAY') ?? 'https://api.megprimepay.com';
const DECIMALS = 6;
const PAID = new Set(['confirmed', 'settled']);
const DEAD = new Set(['expired', 'cancelled', 'declined', 'failed', 'voided']);

const cors = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Headers': 'authorization, x-client-info, apikey, content-type',
};

Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') return new Response('ok', { headers: cors });
  const json = (body: unknown, status = 200) =>
    new Response(JSON.stringify(body), { status, headers: { ...cors, 'Content-Type': 'application/json' } });

  const { orderId } = await req.json().catch(() => ({}));
  const admin = createClient(Deno.env.get('SUPABASE_URL')!, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!);

  // The fulfillment id comes from OUR row, never from the request.
  const { data: order } = await admin
    .from('orders').select('id, status, total_cents, fulfillment_id, payment_amount_uoa').eq('id', orderId).single();
  if (!order?.fulfillment_id) return json({ state: 'unknown' }, 404);
  if (order.status === 'paid') return json({ state: 'paid' });

  const res = await fetch(`${GATEWAY}/api/v1/enforcer/fulfillments/${encodeURIComponent(order.fulfillment_id)}/status`);
  if (!res.ok) return json({ state: 'unknown' }, 502);
  const { data } = await res.json();

  // What was sent for this attempt, and it must still be the order's total.
  const expected = order.payment_amount_uoa;
  const currentTotal = (BigInt(order.total_cents) * 10n ** BigInt(DECIMALS - 2)).toString();
  if (!expected || expected !== currentTotal) return json({ state: 'unknown' }, 409);
  const status = String(data?.status ?? '').toLowerCase();

  if (PAID.has(status)) {
    const paidEnough =
      /^\d+$/.test(data.paid_sum ?? '') &&
      data.notional_uoa === expected &&
      BigInt(data.paid_sum) >= BigInt(expected);
    if (!paidEnough) return json({ state: 'settling' }); // underpaid or still arriving
    // Idempotent: only the first confirm flips it.
    await admin.from('orders')
      .update({ status: 'paid', payment_status: 'paid', paid_at: data.settled_at ?? new Date().toISOString() })
      .eq('id', order.id).neq('status', 'paid');
    return json({ state: 'paid' });
  }
  if (DEAD.has(status)) {
    await admin.from('orders').update({ payment_status: status }).eq('id', order.id);
    return json({ state: status === 'expired' ? 'expired' : 'cancelled' });
  }
  return json({ state: 'settling' });
});
```

Call this endpoint from the page's `onSuccess`. To catch buyers who close the
tab after paying, also call it from a scheduled job (for example a Supabase cron
running every minute) for orders in `awaiting_payment` whose deadline hasn't
passed by more than a few minutes.

## 6. Browser: render and watch

```tsx
import { useEffect, useRef, useState } from 'react';
import { attachCheckout, type CheckoutHandle } from '@megprime/merchant-sdk';
import { supabase } from '@/integrations/supabase/client';

export function PayWithMegPrime({ orderId, onPaid }: { orderId: string; onPaid: () => void }) {
  const ref = useRef<HTMLDivElement>(null);
  const [error, setError] = useState<string>();
  const [canRestart, setCanRestart] = useState(false);
  // Bumping this re-runs the effect. The server decides whether that reuses
  // the current request or issues a new one (section 4).
  const [attempt, setAttempt] = useState(0);

  useEffect(() => {
    let checkout: CheckoutHandle | undefined;
    let cancelled = false;
    setError(undefined);
    setCanRestart(false);

    (async () => {
      // Send the ORDER ID. Never an amount.
      const { data, error } = await supabase.functions.invoke('megprime-create-payment', {
        body: { orderId },
      });
      if (cancelled) return;
      if (error || !data?.fulfillmentId) {
        setError("We couldn't start this payment. Please try again.");
        setCanRestart(true);
        return;
      }

      checkout = attachCheckout({
        fulfillmentId: data.fulfillmentId,
        container: ref.current!,
        theme: 'auto',
        onSuccess: async () => {
          // The UI says paid. The SERVER decides whether it is.
          const { data: c } = await supabase.functions.invoke('megprime-confirm-payment', {
            body: { orderId },
          });
          if (c?.state === 'paid') onPaid();
        },
        onError: (err) => setError(err.retryable ? 'Connection problem, retrying…' : err.message),
        onCancel: () => { /* widget closed. The request may STILL be paid. */ },
        onStateChange: (state) => {
          if (state === 'expired') {
            setError('This payment window expired. Start again to get a new code.');
            setCanRestart(true);
          }
        },
      });
      await checkout.start();
    })();

    return () => { cancelled = true; checkout?.destroy(); };
  }, [orderId, attempt]);

  return (
    <div>
      {error && <p role="alert">{error}</p>}
      {canRestart && <button type="button" onClick={() => setAttempt((n) => n + 1)}>Start again</button>}
      {/* keyed so a restart gets a fresh element: the widget attaches a shadow root, which can't be attached twice */}
      <div key={`${orderId}-${attempt}`} ref={ref} />
    </div>
  );
}
```

The widget renders a QR code, an "Open in the app" deeplink, and live status
inside a shadow root. The app's CSS won't leak into it. **Show the order total
yourself** above the widget, from your own order data. In this mode the widget
doesn't know the currency scale, so it deliberately shows no amount.

For a custom UI instead of the bundled widget, omit `container`. Then draw a QR
from `checkout.snapshot.payUrl` and react to `onStateChange(state, snapshot)`.

### States

| state | meaning |
|---|---|
| `awaiting_payment` | QR is live |
| `settling` | a payer committed and the payment is confirming |
| `paid` | **terminal.** Now confirm on the server (section 5) |
| `expired` | **terminal.** The window closed unpaid. This isn't an error. Offer to start again |
| `cancelled` | **terminal.** The widget was closed. The request may **still be paid** |
| `error` | **terminal.** See `snapshot.error.code` |

`snapshot.consecutiveFailures > 0` means the answer is currently **unknown**. Show
"Reconnecting…", never "Unpaid".

## 7. Edge cases the agent must handle

- **Buyer taps Pay twice, or the network drops mid-create.** The stored
  `payment_attempt_id` is reused, so the server call returns the same request.
  Don't generate a new `client_ref` per click.
- **Buyer wants a new code after `expired`.** The create function sees the dead
  status and issues a new `payment_attempt_id` automatically. "Start again" just
  calls it again. Reusing the old `client_ref` would return the expired request.
- **Widget closed, or the page navigated away.** Closing doesn't cancel anything.
  A buyer with a screenshot of the QR can still pay until the deadline. Keep the
  order `awaiting_payment` and let the server confirmation job settle it.
- **Order total changes after a request exists** (item added, coupon applied).
  The existing request is frozen at the old amount, and resending the same
  `client_ref` would return it unchanged. The create function sees that the
  total no longer matches `payment_amount_uoa` and issues a new attempt. Section
  5 refuses to mark the order paid if the stored amount doesn't match the
  current total.
- **Underpayment.** Handled by the `paid_sum >= notional_uoa` check. Never mark
  paid on status alone.

## 8. Done checklist

- [ ] `grep -r "msk_" src/` and the built client bundle find nothing
- [ ] The secret key is read only from a server-side secret
- [ ] The create endpoint reads the amount from the database, not from the request
- [ ] `client_ref` is a per-attempt UUID stored on the order before the call, reused on retry, and replaced only when the request is dead or the total changed
- [ ] `fulfillment_id` is saved on the order
- [ ] A missing `fulfillment_id` shows an error, not a QR
- [ ] The order is marked paid only by the server, after checking `status` **and** `paid_sum`
- [ ] A background job confirms orders left in `awaiting_payment`
- [ ] `expired` gets a "start again" action, not an error screen
- [ ] The order total is shown in your own UI
